# Skill: implement-story (agent-learning)

Instantiated from the `sidpa-template` skill. The loop (steps 0-9; step 9 runs only for the epic's last story) is mandatory and executed in order; the project facts below reflect confirmed repository conventions.

## Confirmed project facts

- **Base branch:** `main`.
- **Remotes:** `origin` (`https://github.com/mdresch/agent-learning.git`), `upstream` (`https://github.com/microsoft/agent-learning.git`).
- **Isolation:** None needed. State is the file-based `LearningStore`; tests use `tmp_path` / in-memory stores. Worktrees are used (Step 0), provisioned via `uv sync`.
- **Test runner:** `uv run pytest tests/test_<module>.py`. Contracts live in `tests/test_<module>.py` (flat, no per-epic directories).
  - *Note:* The full suite is plain `uv run pytest`, with no `--ignore`. `tests/pmbok` collects once the extras are synced (`uv sync --extra dev --extra examples`; a worktree needs `--all-extras`, see Step 0), and the Spark tests skip without a JVM (LL-013, LL-055). CI (`.github/workflows/tests.yaml`) still runs `pytest --ignore=tests/pmbok` (IMP-056), so a green CI is not the whole suite; run the whole suite locally.
- **Fixtures:** Contract tests using real artifacts (e.g. `DecisionResult` JSONs) must live committed under `tests/fixtures/<module>/`. Never read fixtures from the repo root or from untracked files.
- **Enforcement layer:** None (no pre-commit hooks, no CI contract gate). Step 3 is discipline-only; see `heal-contract-failure`.
- **Spec documents:** ADRs in `docs/adr/`, BRD/FDD in `docs/project-docs/{Business-Requirements,Functional-Design}/`, stories in `docs/user-stories/epic-<N>-*.md`.
- **Log:** `implementation-log.md` at repo root, append-only.
- **Continuous Improvement Register:** `docs/project-docs/Continuous-Improvement-Register.md`. Append-only Markdown OPA for the epic-end positive improvement harvest (`IMP-###`), instantiated from `sidpa-template`.
- **Lessons Learned / OPA Register:** `docs/project-docs/Lessons-Learned-Register.md` governed by ADR-010. Append-only Markdown OPA recording the ADR-010 breakout recap (never a `LearningStore` record type).

## The loop — mandatory, in order

0. **Worktree:** `git worktree add ../agent-learning-story-<X.Y> -b feat/story-<X.Y> main`; run `uv sync --all-extras` in the worktree, then `uv pip uninstall --python .venv/Scripts/python.exe azure-cosmos`, before Step 5; accept a RED only after reading its message: it must name the symbol the story adds, not a missing package (LL-033, LL-055). Before creating it, confirm the story's BRD, FDD and stories are approved, and run `git status --short` in the base checkout to commit or stash anything the story depends on, because a worktree forks from committed state only (LL-010). Confirm with `git log -- docs/policy-shapes` that the story's approval records are committed before the first code commit, and that the PR will show them (LL-027). Invoke this skill at the start of the story and re-read a step before doing it; record a missed step as a deviation in the log, and never claim a result (such as "observed RED first") that did not happen (LL-028).
   - **A branch or worktree for the story already exists = a run was already started (LL-042). Do not adopt it and do not implement again.** Stop `implement-story` at Step 0, inspect it read-only (`git worktree list`, `git status --short`, `git log main..feat/story-<X.Y>`, the story's entry in `implementation-log.md`), tell the human what is there, and continue with `heal-contract-failure` on the existing work, starting from its Step 1 (Intent). Existing work is evidence, not a verified contract: re-walk ADR, BRD, FDD and story to the contract, the component skill and the code in order, and show the contract able to fail (RED) before relying on it. Never change a test or code only to turn a failing check green, and never commit leftover uncommitted work as this run's own without that walk. Fresh heal branch and worktree, named for the story, as Step 0.
1. **Ingest:** Story (`Status: Ready`), ADR, BRD, FDD. The BRD, FDD and stories must be approved, not only marked Ready by their author (LL-010). Hierarchy: ADR > BRD/FDD > Story. If a story has no code deliverable (operational/governance exercise), record findings in the appropriate register rather than forcing code. For every data source or path the story names as committed, run `git ls-files <path>` (and `git check-ignore <path>` if that is empty); if it is not tracked, amend the story's wording and record the gap as an open question before building (LL-037; Stories 19.7 and 20.6 both found a git-ignored "committed" store late). Do the same for every code path the ADR, FDD or story names (`git ls-files <path>`): Epic 22 named `src/agent_learning/weight_compiler.py` for seven stories while the module lives in `src/agent_learning_ext/` (LL-050). Amend acceptance criteria through `scripts/stage16_amend.py` before Step 3, never after the contract exists; a behaviour the criteria do not state is an interpretation in the test docstring (LL-011), not an edit to the story. When a spec says a constructed member, family or value meets a gate, run that example through the real gate function now, record the result in the spec, and amend the spec before writing the contract if it fails (LL-036).
1b. **Pre-Flight Specification & Contract Readiness Gate:** Run the automated Bayesian specification gatekeeper before stating intent or writing RED contracts:
    ```bash
    uv run python scripts/spec_gate.py <X.Y>
    ```
    The spec gate audits the story's acceptance criteria against adversarial checks (specification completeness, None-safety, boundary behavior, empty collections, non-finite domain checks, testability, precision tolerances, Invariant 6 upstream fork purity, and architectural boundaries), applies Epic 14 critique deltas, and resolves a calibrated Bayesian readiness decision.
    - **If the gate halts (`HALTED / SPEC AMENDMENT REQUIRED`):** Stop and resolve ambiguities with the maintainer or amend the specification before proceeding.
    - **If the gate passes (`PASSED / SPEC READY FOR CONTRACTS`):** Record all recommended interpretations ($I_1, I_2, \dots$) from the output. These must be explicitly documented in the RED contract test docstring (Step 3) and cited in the PR description (Step 8.1).
2. **State intent:** Intent / Scope / Contract to encode / Explicitly out of scope.
3. **Contract (RED):** One pytest per Acceptance Criterion; header docstring naming Story, ADR, BRD, FDD, and all interpretations ($I_1, I_2, \dots$) generated by `scripts/spec_gate.py`; fixtures loaded from `tests/fixtures/<module>/`. Run and verify failing (RED) before implementing. If a test asserts behavior the acceptance criteria or the design do not state, record it as an interpretation in the test docstring and the log, and amend the FDD or the open questions (LL-011). Run a normative pattern on every case its prose claims before writing the test, and pin the pattern's actual behavior (LL-022). Read documents inside the helper or test, with an assertion that names the missing file, never at import time (LL-023). Observe RED by temporarily breaking the behaviour under test (remove the guard, zero the update), confirm the named tests fail, restore the file, check that `git diff main -- src` is empty, and record how RED was obtained (LL-035). Derive stable digests with `hashlib.sha256`; `hash(` in a test file is a finding (LL-029). Compare a container of tuples one key at a time; `pytest.approx(<dict of tuples>)` is a finding (LL-039).
4. **Component skill:** Create or update `.claude/skills/<component>/SKILL.md` (governing ADRs/Stories, contract files, load-bearing constraints, call sites). Required Definition-of-Done item.
5. **Implement (GREEN):** Minimal code — no speculative generalization. Write code that contains backslashes or escape sequences with the file-write tool, not a shell heredoc, and read the pattern back (LL-025).
6. **Validate:** Run the story contract, then full suite (plain `uv run pytest`; see the test runner note). If the change adds a step or entry, changes a count, or completes something another document describes as pending, grep the repo for the old number or phrase and update every occurrence in the same change (LL-007). If the full suite cannot run, record in the log which paths were excluded, why, and the resulting count, and never call that count the entire suite (LL-013). If a gate's tool is missing, try `uvx <tool>` before skipping it; skip only if that fails, and record the gate as not run, with the reason (LL-030). Run `ruff check --fix` only on files the change created; on existing files run `ruff check` and read `git diff --stat` for unexpected churn (LL-026).
7. **Commit & log:**
   - **Optional trap note:** If something surprising happened in this story, jot a one-line note for the epic-end breakout recap (ADR-010 §4.1). Optional, never a gate; do not write an `LL-###` entry per story.
   - **Commit:** Commit implementation, test contracts, and component skills.
   - **Audit log:** Commit the implementation first. Then append the entry to `implementation-log.md` with the hash of that commit, in a follow-up commit. Do not amend the implementation commit after logging it: an amend changes the hash and leaves the log citing a commit that never reaches `main` (Epic 2's `61bf203`). Fix a wrong entry in an unmerged branch by editing it; once merged, append a dated correction entry instead.
   - **Status register:** After the audit-log commit, update `docs/project-docs/Project-Status-Register.md` §1 ("Last … completed" / "Next … to implement" / "Session close-off checkpoint") to match, citing merged PRs, commits and `implementation-log.md`, not a document's own `lifecycle_stage`.
8. **PR, Q review, amendments, Bayesian gate, and merge:** the story ends on `main` only after Amazon Q has nothing further to add and the Bayesian PR Gatekeeper approves.
   1. **Open the PR.** Push `feat/story-<X.Y>` to `origin` and run `gh pr create --repo mdresch/agent-learning --base main --head feat/story-<X.Y>`. The description lists the summary, the governing acceptance criteria and any ADR/BRD/FDD rule a reviewer could plausibly challenge, quoted verbatim (Amazon Q sees only the diff and the PR text, never the specs, so an unquoted rule invites a finding the spec already answers), every interpretation (I1, I2, ...) generated by `scripts/spec_gate.py` that needs confirming, and the test plan, naming any paths excluded from the suite and why. Always pass `--repo`: without it `gh` can target the upstream repository, and a pushed branch then fails with the misleading "No commits between main and ..." (LL-018).
   2. **Request the review.** Comment `/q review` on the PR (`gh pr comment <n> --repo mdresch/agent-learning --body "/q review"`). To get an answer for a later commit, comment it again after each push. On Windows Git Bash, prefix the command with `MSYS_NO_PATHCONV=1` (or use PowerShell or `--body-file`): otherwise a leading `/` is rewritten into a path, so `/q review` is posted as `F:/Program Files/Git/q review` and Q never sees it. Afterwards read the posted comment back and confirm it starts with `/q`, and accept a reply only when it is for the head commit the command named (LL-021). The command must be the first characters of its own comment: a `/q` placed on the last line of a longer triage comment got no reply (LL-016). Post the triage as one comment and the `/q` request as another.
   3. **Read the result.** `gh pr view <n> --repo mdresch/agent-learning --json reviews,state,mergeStateStatus` for the summary and `gh api repos/mdresch/agent-learning/pulls/<n>/comments` for the inline findings. Check which commit each comment is on. Q only ever posts `COMMENTED`; it never approves, so a clean state needs an explicit verdict (step 6).
   4. **Triage every finding against the repository before acting.** Accept what the code or the spec supports. Decline what it does not, with a one-line reason in the PR. A reviewer's claim is not evidence: confirm it by reading the code, running the case, or checking the cited ADR. For control-flow claims, trace whether execution can actually reach the alleged use: an exception not caught by a `try` propagates and cannot continue to a later `return`. Distinguish an unreachable crash claim from a harmless defensive hardening recommendation. Record each finding in the fixed shape of step 7 as you triage it, so the decisions can later be replayed as learning data (ADR-036). Check each claim in a confirmation against the head commit, as with a first-round finding; log the ones that are stale or out of scope as noise, with the reason (LL-031).
   5. **Fix and re-review.** Fix accepted findings in new commits on the story branch. Do not amend or force-push the implementation commit (the log cites its hash). Re-run the story contract and the full suite, push, and comment `/q review` again.
   6. **Repeat 2 to 5 until Q has no further additions**, meaning all of: Q's latest review is on the current head commit; it reports no blocking defect and no new finding; no inline comment on the head commit is unaddressed. Ask for the verdict with `/q review` on the head commit, the only Q command; `/q confirm` is not one (LL-004). Silence is not a clean review: if Q has not answered the latest request, wait or ask the human, and do not merge. After three rounds, or if Q repeats a finding that was declined, stop and ask the human.
   7. **Record the review.** Before merging, add a bullet to the story's `implementation-log.md` entry (it is still unmerged, so it can be edited) listing the Q rounds, the findings accepted, and the findings declined with reasons. List each finding on one line in this shape: `Q-<PR>-<n> | <claim type> | verified: yes/no/partial | decision: accepted/declined/deferred | <one-line reason> | fix: <commit or none>`. Claim types: logic error, crash risk, test gap, documentation, style. Do not guess a field; write `unknown`. A claim type outside that list is not accepted by `review_triage` and fails three foreign contracts on `main`, so after writing or editing triage lines run `uv run pytest tests/test_review_triage.py tests/test_critique_replay.py` before committing (LL-049). A review with no findings is one prose bullet in the story's entry (round, head commit, Q's verdict), never a `Q-<PR>-<n>` line (LL-034).
   8. **Mandatory PR Gatekeeper Review:** Run the automated Bayesian PR Gatekeeper before any merge:
      ```bash
      uv run python scripts/pr_gate.py <n>
      ```
      The gatekeeper evaluates CI checks, Invariant 6 upstream file purity, ingests reviewer critique into Bayesian log-odds shifts and doubt adjustments via Epic 14, and verifies robust utility margin $\ge +0.05$. If the gate halts (`HALTED / REVISIONS REQUIRED`), address the blocking items before proceeding.
   9. **Merge to `main`:** Prefer merging the base story first. A stacked PR gets no CI until it targets `main` and is unverified: after the base merges, change its base to `main`, merge `main` into the branch, rerun the full suite and wait for the CI checks before the gate (LL-038). When the gatekeeper reports `PASSED / APPROVED TO MERGE` and `mergeStateStatus` is `CLEAN`, merge via the gatekeeper:
      ```bash
      uv run python scripts/pr_gate.py <n> --merge
      ```
      (or `gh pr merge <n> --repo mdresch/agent-learning --merge`). Then verify `gh pr view <n> --repo mdresch/agent-learning --json state` reports `MERGED`; run `git checkout main` and `git pull --ff-only origin main`; and verify the feature branch tip is an ancestor of `main` before cleanup. Remove the story worktree (`git worktree remove ../agent-learning-story-<X.Y>`, without `--force`), then delete the local feature branch with `git branch -d feat/story-<X.Y>`. If the remote branch still exists (GitHub may already have deleted it), delete it with `git push origin --delete feat/story-<X.Y>`. Never force-delete a branch or worktree; if the merge/ancestry check fails or cleanup finds uncommitted work, stop and report rather than discarding it. The human can withhold or override the merge or cleanup at any point by saying so.
9. **Breakout & recap (last story of the epic only):** After contracts are verified (Step 6) and Step 8 has reached "Q has no further additions" on the epic's final story PR (Q comments, it never approves), hold the light breakout recap defined in ADR-010 §4.1: how the code was created from the stories, covering unexpected traps, subtle defects and review findings. This is not the formal Stage 15 review, which is separate. Record each lesson as an `LL-###` entry in `docs/project-docs/Lessons-Learned-Register.md` (required fields: title, trap, root cause, rule, propagation target, which may read `Tier 1 only`; include Epic / Story so the Phase Close filter matches), or record a short no-new-lessons sign-off entry (Epic/Phase containing `no-new-lessons`, propagation target `Tier 1 register sign-off`). An Autonomous Breakout Facilitator may draft these, but a human accepts them (ADR-010 §4.7). Consider propagating component-specific rules to `.claude/skills/` (Tier 2) and universal rules to `sidpa-template` (Tier 3). Commit the register change with the epic's closing PR or a follow-up docs commit. Before closing the recap, check that every Tier 2 target named by the previous epic's `LL-###` entries contains its LL id (`grep -c "LL-0xx" <file>`); a missing id is a finding, and a new entry's Tier 2 edit goes in the same PR as the entry (LL-041). To claim an omission in the audit, read the unfiltered source (for example `grep -c` on the whole entry) and quote what you saw; a filtered output only supports "not found in this view" (LL-032). Skip this step for every story that is not the epic's last.
   - **Code & methodology recap (asked first):** Before the lessons, answer the code question in the Epic Recap Log of `docs/project-docs/Continuous-Improvement-Register.md` (section 3, field list there): which methodology the epic implemented (catalog number and ADR), the modules, public names and commands delivered, the design worth keeping, the review findings counted per module with `review_triage`, the known gaps in the code, where in this project it could apply and how little data limits it, what a runnable demonstration would show, and what is verified versus only claimed. Write it from the merged code and the review record. A `Q-<PR>-<n>` finding belongs here as a statement about the code it concerned; a lesson about git, the environment or the review workflow belongs in an `LL-###` entry, and a lesson is not a substitute for this recap. Never change a methodology's catalog state or a hypothesis status here; those go through ADR-024.
   - **Positive posture (improvement cadence):** Also ask the cadence question: *"What improvement ideas, architectural simplifications, developer-experience boosts, or product opportunities emerged during this Epic that could add value to upcoming Epics or roll into the Intent Refinement Proposal for the next phase?"* Record each idea as an `IMP-###` entry in `docs/project-docs/Continuous-Improvement-Register.md` (Originating Epic, Title, Category, Description, Target Benefit, and Disposition: `In-Flight Candidate` or `Rolled into Phase Next Intent Refinement`), or append the sign-off `Epic [N] Recap: No new improvement ideas identified.` to its Epic Recap Log. Record only ideas the epic actually surfaced. Ideas dispositioned `Rolled into Phase Next Intent Refinement` are harvested at Stage 18.

**Session-boundary note (not step-gated):** a model or session limit can end work abruptly, mid-story, without warning, not only at Step 9. At every natural pause (a decision made, a correction applied, before work that will take many steps) update `docs/project-docs/Project-Status-Register.md` §1, especially the "Session close-off checkpoint" row, with the real current state, cited against merged PRs, commits, `implementation-log.md` and the gate episodes (sidpa-template `docs/sequence-and-lessons.md` §8, rules 23 and 24). A document's own `lifecycle_stage` frontmatter is an authoring-time label, not the live position. Cheap, frequent insurance, not a gate.

## Definition of done

Pre-flight specification gate (`scripts/spec_gate.py`) passes with approved Bayesian margin and interpretations documented; contract exists, observed RED, and passes; full suite passes; fixtures are committed under `tests/fixtures/<module>/`; component `SKILL.md` is current; for the epic's last story only, the ADR-010 breakout recap is held and recorded in `docs/project-docs/Lessons-Learned-Register.md` (an `LL-###` entry or a short no-new-lessons sign-off entry) and in `docs/project-docs/Continuous-Improvement-Register.md` (the Code & Methodology Recap in its Epic Recap Log, and an `IMP-###` entry or a no-new-ideas sign-off); traceability is accurate; `docs/project-docs/Project-Status-Register.md` §1 reflects the real current state (check this even when the story is not the epic's last); `implementation-log.md` entry is recorded with resolved commit hash; the PR has reached "Q has no further additions" with accepted findings amended and declined ones explained; `scripts/pr_gate.py` passes with approved Bayesian margin; and the PR is merged to `main` with the worktree removed.
