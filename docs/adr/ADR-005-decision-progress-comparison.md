# ADR 005: Decision-Progress Comparison and Regression Healing

## 1. Executive Brief
Reviewing ADR-002 found two real structural defects (out-of-order §4 numbering, an imprecise invariant) and three worthwhile additions; after fixing them, re-running the `approve-adr` policy's `task-policy-decide` with evidence updated to reflect those fixes produced a genuine, measured result: `approve_adr`'s robust utility rose from 0.841 to 0.875, while `reject_adr`/`request_revision_before_decision` both fell, widening the decision margin from 0.744 to 0.817. That comparison was done entirely by hand — saving one JSON file, hand-authoring a second decision-frame, and writing a throwaway Python diff script. This ADR proposes making "did this revision actually help, and by how much" a first-class, reusable capability instead of an ad hoc script — generalized from a single before/after pair to a full **sequence** of revision passes, with a bounded, human-escalating **heal step** triggered specifically on regression (never on progression) — and records why that capability should stay **stateless and caller-driven**, not a new persisted record type, given what ADR-001 and ADR-002 already decided.

## 2. Status
**Accepted (2026-10-23)** — drafted 2026-10-23, revised across two passes (precondition validation, exhaustive/mutually-exclusive taxonomy with an exclusivity proof, "heal orchestrates, doesn't remediate" clarification), approved by Menno. The real `approve-adr` policy's robust utility for this decision: 0.864 vs. 0.042 (reject) and 0.056 (revise).

## 3. Context
- `DecisionResult` (`decision.py:316-334`) has no timestamp field at all — no `created_at`, no `decided_at` — and is never persisted by `LearningStore`. Confirmed directly: the five record types `LearningStore` persists (episode, metric result, reward, policy snapshot, training run — ADR-002 §4.1) do not include decision results. A `DecisionResult` only leaves a durable trace if a human adjudicates it and the caller separately calls `task-episode-register` — and even then, the registered `Episode` stores a human-readable summary (`assistant_output`, `input_summary`), not the structured per-criterion evidence (`DecisionFrame.criteria`/`.options`) that produced it.
- This statelessness is not an oversight; it follows directly from two decisions already made. ADR-001 §4.2: a `full`-authority decision is "reasoning from the *current* evidence," not an accumulating process. ADR-002 §4.1/§4.6 (as revised this session): `LearningStore` is deliberately narrow — exactly five record types — and explicitly **not** a query/analytics/general-purpose store. Adding decision-result history as a sixth persisted type would cut directly against both.
- The real comparison just performed (ADR-002's before/after) only worked because I happened to redirect the first `task-policy-decide` call's stdout to a file (`adr-002-decision-result.json`) before revising the ADR, then diffed it against a second run's output with a one-off `python -c` script reading both files' `assessments[].robust_utility`. Nothing in the CLI or SDK computes or prints that delta; nothing guarantees the "before" file still exists by the time someone wants to compare.
- `OptionAssessment` (the `assessments` entries inside `DecisionResult`) already carries everything a comparison needs per action: `robust_utility`, `expected_utility`, `uncertainty`, `feasible`, `ruled_out_by` — confirmed by direct use in this session's own ADR-002 comparison. No new field needs to be added to compute a delta; the two numbers just need to be brought together and subtracted, which nothing currently does.

## 4. Decision

### 4.1 Build a stateless comparison function, not a new persisted record type
Given two `DecisionResult` JSON files — a "before" and an "after" — compute, per action: the `robust_utility` delta, the `expected_utility` delta, the `uncertainty` delta, and the overall margin delta (winning action's robust utility minus the next-best's, before vs. after). This is the exact computation performed by hand for ADR-002; formalizing it does not require tracking anything the SDK doesn't already track per-call.

**Precondition, stated explicitly rather than assumed:** the comparison is only valid between `DecisionResult`s that share the same `(agent_id, task_id)`, the same `decision_authority` (`OptionAssessment`'s fields are only populated by the `full`-authority resolver — `decision.py:233-253` — so a `low`-authority result has nothing meaningful to compare), and an identical action taxonomy. The utility must check this and raise rather than silently compute a delta across unrelated policies or a changed action set.

### 4.2 The caller retains both files; the SDK adds no new persistence
Exactly like `--decision-frame` already works (caller supplies JSON in, caller is responsible for the artifact), a comparison utility takes two caller-supplied `DecisionResult` files and computes a delta — it does not read from or write to `LearningStore`. This keeps the five-record-type boundary (ADR-002 §4.1) and the "not a query/analytics platform" non-goal (ADR-002 §4.6) intact. The real cost of this choice is named honestly in §6, not hidden.

### 4.3 Compare every action, not just the winner
The ADR-002 case was informative specifically because `reject_adr` and `request_revision_before_decision` both *fell* while `approve_adr` rose — a stronger, more specific signal than "the winning action's score went up" alone would have been (a revision could in principle raise every option's score roughly equally, which would widen no real margin). Any comparison utility must report every action's delta, not only the proposed/selected one.

### 4.4 Generalize from one before/after pair to a tracked sequence
A real revision process is rarely exactly two passes. **The primitive operation is the pairwise comparison defined in §4.1; a sequence introduces no new comparison semantics** — it is that same pairwise computation applied to every consecutive pair in an ordered list of `DecisionResult` files, nothing more. The comparison utility takes that *list* and reports the step-by-step delta between every consecutive pair — not just first-vs-last. **Each consecutive pair is classified independently; a step's classification is never retroactively revised by a later step** (a V1→V2 regression stays a regression even if V2→V3 recovers past V1's margin) — this is stated explicitly so a future implementer doesn't attempt cumulative trend-smoothing instead of the simpler, more legible pairwise record.

**Corrected here to be exhaustive and mutually exclusive** (the original three-way split had a real gap: a step where the leading action's own `robust_utility` dips slightly while the runner-up falls *more*, actually widening the margin, satisfied none of the three categories as first drafted). With a small tolerance `ε` to avoid treating noise as signal:
- **regression**: the leading action changed, **or** became infeasible (`feasible: false`), **or** the margin narrowed by more than `ε`, **or** the leading action's own `robust_utility` fell by more than `ε` (regardless of what the margin did);
- **progression**: the leading action is unchanged and feasible, and *either* the margin widened by more than `ε` with the leading action's `robust_utility` not falling by more than `ε`, *or* the leading action's `robust_utility` rose by more than `ε` with the margin not narrowing by more than `ε`;
- **flat**: the leading action is unchanged, and both the margin delta and the leading action's `robust_utility` delta fall within `[-ε, +ε]`.

This reuses exactly the per-action data model from §4.1/§4.3; a sequence is just that comparison applied pairwise, nothing structurally new.

**Mutual exclusivity is provable, not just asserted — no tie-break rule is needed.** `progression` requires the leading action unchanged *and* feasible, which already rules out `regression`'s first two disjuncts (action changed; infeasible). Of `progression`'s two remaining branches: branch 1 requires the margin widened by more than `ε`, which is the direct negation of `regression`'s "margin narrowed by more than `ε`"; branch 2 requires the leading action's utility rose by more than `ε`, the direct negation of `regression`'s "utility fell by more than `ε`." Each `progression` branch also requires the *other* delta not move against it by more than `ε`, closing the remaining disjunct. No combination of deltas can satisfy both `progression` and `regression` simultaneously — a case that looks ambiguous at first glance (e.g., the leading action's utility dips slightly while the margin still widens because the runner-up fell more) resolves to `regression` outright, via its fourth disjunct, not to a tie.

### 4.5 Regression triggers a bounded, human-escalating heal step — never a silent auto-revert
When a step in the sequence (§4.4) classifies as a regression, that is a real signal the latest revision made the case for the leading action *weaker*, not stronger — worth surfacing immediately, not silently absorbed into "well, we'll catch it at final review." **Named precisely: this "heal step" orchestrates a response — detect, flag, bound retries, escalate — it does not itself heal anything.** The actual remediation (the next revision) is produced entirely outside this mechanism, by whoever or whatever is doing the editing; calling it "healing" describes the workflow's purpose, not a claim that the SDK performs the repair. The heal step mirrors this session's own `heal-contract-failure` precedent (ADPA/sidpa-template) exactly, rather than inventing a new shape:
1. **Flag the regression immediately**, naming which criteria/evidence moved against the leading action, not just that the number fell. **Confirmed directly, not assumed: this is fully supportable from `DecisionResult` JSON alone.** `OptionAssessment.criteria` (`decision.py:233-253`, a tuple of `CriterionAssessment`) is serialized in `to_dict()` and carries each criterion's own `support` value — confirmed against this session's own real `task-policy-decide` output every time it ran. Per-criterion attribution does not require the original `DecisionFrame` file as a third input; the two `DecisionResult`s already contain it.
2. **Attempt a bounded number of corrective passes** (a small fixed cap, e.g. 2-3 — the same bounded-retry shape `heal-contract-failure` uses for a failing contract) — each attempt re-runs the comparison after the next revision.
3. **Escalate to human review if the cap is exhausted without returning to progression** — exactly `heal-contract-failure`'s own "escalate, don't loop forever" rule.
4. **The SDK does not generate the corrective fix itself.** Detecting and classifying regression is the SDK's job; producing the next revision is the calling agent's or human's job, the same division of labor `heal-contract-failure` already uses (the skill tells an agent to retry; it doesn't regenerate the agent's code for it). This utility never edits the ADR/BRD/FDD/Story being revised — it only ever reads two or more `DecisionResult` files a caller already produced.
5. **No automatic rollback of the document itself.** An explicitly rejected design (§5): silently reverting a human-authored revision because its score fell would override real editorial judgment with a number that can be wrong (e.g., a revision that correctly disclosed a harder truth, lowering `consequences_honest`'s support while making the document *more* accurate, not less). Flag and escalate; never auto-revert content a human wrote.

## 5. Alternatives Considered

| Alternative | Reason for rejection |
|---|---|
| Add `DecisionResult` as a sixth persisted record type in `LearningStore` | Directly contradicts ADR-002 §4.1 (exactly five record types, deliberately) and §4.6 (not a general persistence layer) — both decided this session, not historical constraints being reinterpreted away. |
| Fold "the prior decision" into `Episode.metadata` at registration time | Doesn't cover the case that actually motivated this ADR: comparing two **decide-only** runs before either is adjudicated or registered as an episode at all (exactly what happened across the two ADR-002 passes — neither was ever registered, by design, since Menno hadn't approved either). |
| Leave it as ad hoc scripting (the status quo) | Works once, is not reusable, has no standard output shape, and depends on the person doing the comparison remembering to have saved the "before" file in the first place — exactly the fragility this ADR exists to remove. |
| On regression, automatically revert the document to the prior, better-scoring revision | Would let a number silently override real editorial judgment (§4.5's point 5) — a revision that honestly discloses a harder truth can legitimately score lower while being the correct edit. Flagging and escalating preserves human judgment; auto-reverting removes it. |
| Let the heal step itself generate the corrective revision (e.g., an agent automatically rewrites the ADR on regression, in a loop, with no cap) | Mirrors exactly the failure mode `heal-contract-failure` was built to avoid elsewhere in this session's work: an uncapped retry loop with no escalation path. Capping attempts and escalating to a human on exhaustion is the same discipline applied here, not a new one invented for this ADR. |

## 6. Consequences

### Positive
- Makes "did this revision help" a measured, auditable number instead of a subjective impression — directly reusable for every future ADR/BRD/FDD/Story revision pass in this governance chain, not just ADR-002's.
- No new persisted state, no new record type, no change to `LearningStore`'s contract — consistent with ADR-002 as just revised.
- Reports per-action deltas, catching the more informative signal (margin widening from both sides) rather than only the winning action's movement.
- Generalizes to real multi-pass revision chains (§4.4) instead of only ever comparing two points, and gives regression a real, bounded response (§4.5) instead of silence until final review.

### Negative
- The comparison is only as good as the files the caller actually kept. Nothing in the SDK prevents a "before" snapshot from being lost, overwritten, or never saved in the first place — this ADR deliberately does not solve that with persistence (§4.2), so the caller's own discipline is the only safeguard.
- The heal step's regression classification (§4.4) is a heuristic (margin width, leading-action identity) — it can misfire on a revision that is correct but strategically lowers one criterion's support to raise overall honesty (named explicitly in §4.5, point 5). The human-escalation path exists specifically because this heuristic is not infallible, not despite it.
- A fixed retry cap (§4.5, point 2) means a legitimately hard-to-fix regression still escalates rather than resolving — by design, not a flaw to patch later.

## 7. Architectural Invariants

1. Decision-progress comparison is strictly stateless — it reads caller-supplied `DecisionResult` artifacts and never reads from or writes to `LearningStore` (§4.1, §4.2; ADR-002 §7 Invariant #2/#6).
2. Every comparison validates that its inputs share the same `(agent_id, task_id)`, the same `decision_authority` (`full`), and an identical action taxonomy before computing any delta — mismatched inputs raise, never silently compute a meaningless delta (§4.1).
3. Deltas are computed across the full action set (`OptionAssessment` per action), never only for the winning/proposed action (§4.3).
4. Each consecutive pair in a sequence is classified independently and permanently — a step's classification is never revised by a later step's result (§4.4).
5. The progression/regression/flat classification is exhaustive and mutually exclusive by construction (§4.4) — every possible combination of margin delta and leading-action-utility delta lands in exactly one category.
6. Regression handling is bounded and advisory — the SDK classifies regressions and enforces a retry cap before escalating to human review, but never generates document edits or auto-reverts caller artifacts (§4.5).

## 9. Open implementation questions — not resolved here
- Whether this ships as a new CLI subcommand (`agent-learn task-policy-compare --sequence <file1> <file2> ...`) or a flag on the existing `task-policy-decide` is a real interface choice left open.
- The exact retry cap (§4.5, point 2) and the tolerance `ε` (§4.4) are tuning parameters, not architectural decisions — left for whoever builds this to set from real usage, not guessed here.
- **Illustrative only, not a commitment**: a plausible output shape per pairwise step would carry `pair_index`, `classification` (`progression`/`regression`/`flat`), `leading_action_before`/`leading_action_after`, `margin_before`/`margin_after`/`margin_delta`, and `action_deltas` (per-action `robust_utility`/`expected_utility`/`uncertainty` deltas, §4.3). Sketched here only so whoever builds this isn't starting from nothing; the exact shape is implementation's call.
