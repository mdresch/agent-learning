# ADR 004: Authority-Migration History — A Forward Comparison Snapshot, Not a Retroactive Replay

## 1. Executive Brief
When a `TaskPolicy` migrates from `low` to `full` authority (ADR-001 §4.3), nothing today re-examines the policy's existing episode history under the newly active authority — migration is a pure configuration flip. The proposal that prompted this ADR: retrigger a recalculation of the policy's historical `low`-authority episodes under the newly determined `full` authority, so the migration itself produces evidence that it was justified. Checked directly against the data actually captured today, that literal recalculation is not possible — no historical `low` episode has the evidentiary basis `full` authority's resolver requires, and nothing resembling it was ever captured. This ADR records why, and proposes the real thing that **is** buildable in its place: a single, cheap, frozen comparison snapshot taken at the moment of migration, with its limits named honestly rather than oversold as the recalculation that was actually asked for.

## 3. Context
- `task-policy-authority-set` (ADR-001 §4.3) changes a policy's active authority in place and is real and reversible — but it is, today, only a metadata write. No code path re-evaluates anything that happened before the switch.
- `DecisionResolver.resolve()` — the mechanism behind `full` authority — requires a `DecisionFrame` (`decision.py:135-144`): `task`, `criteria: Sequence[DecisionCriterion]`, `options: Sequence[DecisionOption]`, `constraints`, `minimum_margin`, `uncertainty_penalty`, `max_uncertainty`. This is real, structured, per-option evidence — not a label or a score.
- `TaskPolicy.decide()` (`decision.py:874-888`) enforces that a `low`-authority decision is never given a `DecisionFrame` at all — passing one raises `ValueError` ("low decision authority uses learned policy evidence, not a decision frame"). So no `low`-authority episode, past or future, has ever had this evidence constructed for it in the first place. There is nothing to retrieve, because nothing was ever built.
- `Episode`'s only decision-time input field is `context_features: Dict[str, Any]` (`types.py:146`), described in its own docstring as "the input the policy used to choose its action (so the learner can replay the decision)." **Checked directly, and that description does not hold for the `low` path**: `decide()`'s `low` branch (`decision.py:890`) builds `SoftmaxPolicy.from_snapshot(self.snapshot())` — using only the durable `PolicySnapshot`'s own stored logits, never `context_features`. `SoftmaxPolicy` is confirmed non-contextual by its own module docstring (`policy/softmax_bandit.py:1-6`): "one logit per action... the action space is fixed at construction time." `context_features` is populated by the caller (`capture.py:132/155`) and consumed elsewhere for reward shaping (`metrics/local.py:34-51`) — real, but not decision evidence for either authority. **Worth stating plainly, and more strongly than "stale": `types.py:146`'s own docstring is materially incorrect with respect to current behavior, not merely imprecise** — it claims a replay capability that does not exist today and, per §4.1, cannot exist for already-logged episodes no matter what code is added later. That is almost certainly what would lead a future reader of the code (not just of this ADR) to propose the exact retroactive replay this ADR rejects. Naming that here, rather than only in this ADR's own reasoning, is meant to stop the same proposal from resurfacing from a fresh reading of `types.py` alone.
- Conclusion from the above: there is no reconstructable path from a historical `low`-authority `Episode` to a `DecisionFrame`. Recalculating such an episode under `full` authority would mean inventing criteria, options, and constraints that were never actually weighed at decision time — not a replay of a real decision, a fabrication of one. ADR-001 §9's Amendment Log already drew this exact line once (disclosing a real gap vs. silently rewriting to look resolved); this ADR applies the same discipline to the idea of a fabricated replay.
- **Asymmetric finding, named but not pursued here:** because `SoftmaxPolicy` is non-contextual, its entire learned state at any instant is just the snapshot's stored logits — nothing episode-specific is needed to ask "what would the current learned policy choose." That makes the *reverse* comparison (what would `low` say about a historical `full`-authority decision) mechanically trivial, unlike the direction actually proposed. Not explored further here — a narrower, separate question, flagged only so it isn't silently assumed equally hard.

## 4. Decision

### 4.1 No retroactive replay of historical `low`-authority episodes
Historical `low` episodes are not recalculated under `full` authority. The evidentiary basis required (`DecisionFrame`'s criteria/options/constraints) does not exist for them and cannot be reconstructed from what was actually captured (`context_features`, conversation history, tool calls) without fabricating it. A comparison built on fabricated evidence would look rigorous while being worthless as a faithful counterfactual — worse than no comparison at all, because it manufactures false confidence in the migration it's supposed to be validating.

### 4.2 A migration instead captures one frozen comparison snapshot inside `PolicySnapshot.metadata`, not a per-episode replay and not a sixth record type
On `low → full` migration, persist a lightweight `MigrationRecord` (`policy_version_at_migration`, `action_probabilities_at_migration` — the softmax distribution the policy had actually converged to — `from_authority`, `to_authority`, `migrated_at`) **inside the existing `PolicySnapshot.metadata` field** — the same place `decision_authority` itself already lives (ADR-002 §3) — rather than introducing a sixth top-level record type on `LearningStore`. This is a real constraint, not a styling choice: ADR-002 §7 Invariant #2 already fixed the record-type count at exactly five, and `MigrationRecord` as a new standalone type would reopen that decision rather than build within it. **`policy_id` is deliberately not one of `MigrationRecord`'s own fields** — confirmed intentional, not an oversight: it would be redundant denormalization, since the enclosing `PolicySnapshot` that holds this metadata already carries its own `id`/`task_id`, and `policy_version_at_migration` is what uniquely anchors *which* snapshot version the transition occurred at across future `advance_version()` calls. Because the bandit is non-contextual (§3), this one frozen distribution **is** the complete representation of "everything `low` authority had learned," for every decision from that point forward — no per-decision recomputation, no new evidence capture, and no new storage container is required to build it. **Each migration event appends a new, immutable record** — a policy that oscillates `low → full → low → full` accumulates multiple `MigrationRecord`s, never overwrites or "refreshes" an earlier one; each represents the policy's observed state at exactly the instant of that transition. **The trigger is exact, not inferred:** a successful `task-policy-authority-set` call (§3) is what creates it — every successful transition appends exactly one `MigrationRecord`, never zero, never more than one per transition.

**What kind of evidence this is, stated explicitly rather than left ambiguous:** `MigrationRecord` is *diagnostic* migration evidence — it documents the learned policy state at the moment authority changed. It is not, by itself, evidence that the migration was correct or justified; it answers "what had the policy converged to," not "was promoting it the right call." Conflating the two would overstate what a frozen snapshot can actually support.

### 4.3 Name the limitation the snapshot does not resolve
`MigrationRecord` answers "how does `full` authority's post-migration reasoning compare to where the bandit had converged" — it does **not** answer "would `full` authority have agreed with each specific historical `low` decision," which is what was actually asked for and is foreclosed by §4.1. Recording this limitation explicitly here, rather than letting §4.2 be read as a substitute for the thing it cannot do.

### 4.4 True historical replay is a separate, larger, future decision — not resolved here
If per-episode retroactive comparison is still wanted, it requires every decision (regardless of authority) to capture a `DecisionFrame`-equivalent evidence record going forward — a real cost (criteria/options assembly even under `low`, which exists specifically to be cheaper than that) weighed against a real benefit, and a decision on its own. Not bundled into this ADR, for the same reason ADR-001 §6 deferred "learning from full-authority decisions" to a future ADR rather than resolving it inline: scoping it now, before anyone has decided whether the cost is worth paying, would force a conclusion ahead of the evidence. Even if adopted, it would only cover episodes logged after it ships — already-logged `low` episodes remain permanently unreplayable, a hard limit, not a staged one.

**Addendum — idempotency rule for that future recalculation process (Menno, 2026-10-23):** if that richer capture is ever adopted and per-episode recalculation becomes real, the process that runs it is a second, independent loop alongside REINFORCE training — triggered specifically by a `low → full` authority transition, not by every policy update. That loop must process each episode **at most once across the policy's entire lifetime**, not once per migration event: an episode already recalculated under `full` authority during an earlier `low → full` migration must not be recalculated again by a later one, even if the policy subsequently migrates back to `low` and forward to `full` again. Two real reasons this matters, not just tidiness:
- **Cost.** Without this guard, every `low → full` migration would re-walk the policy's entire historical episode set, including episodes already covered by a prior migration — cost growing without bound across repeated oscillations instead of being paid once per episode.
- **Consistency.** If the `full`-authority resolver's own criteria or options evolve between two migration events (a real possibility — nothing in this ADR or ADR-001 freezes `DecisionFrame` construction over time), recalculating the same episode twice could produce two different "what full authority would have said" answers for one historical decision, with no principled way to say which is authoritative. Running the recalculation exactly once per episode, the first time it becomes eligible, avoids the ambiguity entirely rather than requiring a tie-break rule to resolve it later.

**Clarified so a future implementer doesn't misread "at most once" as "only on the first migration ever":** on a second `low → full` transition (after oscillating `low₁ → full₁ → low₂ → full₂`), the loop still runs — it is not skipped outright — but processes only the episodes accumulated during the `low₂` window that have never been recalculated, filtering out the `low₁` episodes already covered during `full₁`. The invariant is per-episode, not per-policy.

This governs the future mechanism's shape; it does not change §4.1's finding that this mechanism cannot be built against today's data.

## 5. Alternatives Considered

| Alternative | Reason for rejection |
|---|---|
| Approximate a `DecisionFrame` from `context_features`/`metadata`/`conversation_history` for historical `low` episodes | `context_features` was never decision evidence for either authority (§3) — reconstructing criteria/options from it would be inventing a counterfactual, not computing one. Rejected on the same evidentiary-integrity grounds ADR-001 §9 already applied to itself. |
| Do nothing — leave migration as a pure configuration flip, no comparison artifact at all | The status quo. Rejected because §4.2's snapshot is cheap enough (one record, zero new capture, since the bandit is non-contextual) that there's no real cost justifying skipping it, and it directly serves the same underlying confidence-at-a-trust-elevation-point concern ADR-001 §4.3 already named without building. |
| Mandatory `DecisionFrame`-equivalent capture on every decision retroactively enforced starting now (§4.4's option, adopted immediately rather than deferred) | A real, larger cost/benefit tradeoff (does requiring evidence assembly under `low` authority defeat part of why `low` exists) that deserves its own scrutiny, not a rider smuggled into this ADR's decision. |

## 6. Consequences

### Positive
- Closes the real part of the gap that's actually closable: a migration event now produces evidence instead of being a silent flag flip, at effectively zero marginal cost (one snapshot, not a replay pass over episode history).
- Does not complicate or block BRD-001/FDD-001's REINFORCE-exclusion fix — orthogonal mechanism, no shared code path.
- Honest about what it doesn't do, so a future reader doesn't mistake `MigrationRecord` for the historical audit trail that was actually requested.

### Negative
- Does not deliver the literal recalculation originally proposed — some real value (a true before/after comparison on the exact historical decisions) is permanently unavailable for already-logged `low` episodes, not just delayed.
- If §4.4's richer capture is ever adopted, it adds real assembly cost to every `low`-authority decision going forward, partially eroding the cost asymmetry between `low` and `full` that ADR-001 §4.1 built the two-route design around in the first place — a tradeoff for that future ADR to weigh explicitly, not an assumption this one makes for it.

## 7. Architectural Invariants

1. A historical `low`-authority episode lacking captured `DecisionFrame`-equivalent evidence is never retroactively re-evaluated via synthetic or inferred criteria/options (§4.1) — this is permanent for already-logged episodes, not a temporary gap.
2. No replay mechanism, present or future, may synthesize decision evidence that was not actually captured at decision time — this is the governance principle every other invariant here is an instance of, and it survives any future implementation change (§4.1).
3. `MigrationRecord` lives inside `PolicySnapshot.metadata` on authority transition — it does not add a sixth durable record type to `LearningStore` (§4.2; ADR-002 §7 Invariant #2).
4. Each successful `task-policy-authority-set` transition appends exactly one new, immutable `MigrationRecord` — never zero, never more than one, never overwritten or refreshed (§4.2).
5. `MigrationRecord` is diagnostic evidence of the policy's state at migration time, not evidence that the migration itself was correct or justified (§4.2).
6. If a future `DecisionFrame`-capture capability is ever built (§4.4), any retroactive recalculation loop it runs is idempotent per episode — at most once across the policy's lifetime, regardless of how many times authority oscillates (§4.4 addendum).
