# BRD-013: Subsidiary Plan Approval Gates Before PMP Formalization

**Source ADR:** [ADR-013](../../adr/ADR-013-subsidiary-plan-approval-gates-before-pmp-formalization.md) — Accepted (2026-10-25)  
**Governing Baseline:** none approved yet (`approve-pmp` is not built; see ADR-013 §4.8)  
**Status:** Approved (2026-10-27, Menno) — derived from Accepted ADR-013; adjudicated via `approve-brd` (robust utility 0.752, episode `76353af5-6092-4374-865b-7c2dbd2110cf`).  
**Stakeholders:** Menno (Sponsor/PM/maintainer)  

## Business Need

The first PMBOK baseline (`PMP-BL-v1.0.0`) was synthesized over plans that were generated by a stub client and never judged one by one. Only the integrated `approve-pmp` gate was ever designed, and it has not been built, so a rejection could not say which plan caused it and a stub could reach a baseline unnoticed. ADR-013 inserts a per-plan approval gate (`approve-subsidiary-plan`) between drafting and PMP formalization, binds each approval to the exact content that was approved, lets a change in one plan suspend only the approvals that depend on it, and lets formalization start only when every plan meets the requirement of its route.

This requirement covers the **decision logic that needs no storage and no network**: the content hash an approval is bound to, the technical-integrity findings that rule a plan out, the record an approval leaves, the dependency graph, whether an approval is still fresh, the plan's lifecycle state, and whether formalization may start. It does not cover running the gate from a command line or reading the store (ADR-034), building `approve-pmp`, or the human review itself.

## Business Rules (BRU)

- **BRU-013-01 (An Approval Is Bound to Content):** Each plan has one canonical content hash that is the same on Windows and Linux and does not change when only volatile metadata changes (`last_modified`, `generated_at`, `governance_hash`, `approval_ref`). Editing or regenerating the plan changes the hash and so ends the approval (ADR-013 §4.3, Invariant 4). A plan whose frontmatter cannot be read gets a change-detection hash that is marked as such and can never support an approval (ADR-034 §4.2.2).
- **BRU-013-02 (Technical Integrity Rules a Plan Out):** A plan is ruled out from `approve_plan` outright when it declares a stub or mock generator, contains an unexpanded placeholder, failed to generate or is missing, or has frontmatter that cannot be parsed (ADR-013 §4.2, Invariant 5). Floors, caps and provisional tokens are flags with evidence, never blocks (ADR-011 §3.2). The ruling-out is expressed as a hard constraint a decision frame can carry.
- **BRU-013-03 (One Policy, Human Authority, Minimal Evidence):** There is one policy, `approve-subsidiary-plan`, with the three actions `approve_plan`, `reject_plan` and `request_revision_before_decision`, full authority, and permanent human approval (ADR-013 §4.2, Invariant 2). Each decision leaves an `Episode` whose metadata follows one fixed contract: identifiers, hashes, the human disposition, a run id and a sequence number; never plan text (ADR-034 §4.2.1, Invariant 6). The producer and the reader of that record share one definition so they cannot drift.
- **BRU-013-04 (The Dependency Graph Is One Authoritative Graph):** The dependency graph of the nine plans is a single global graph. A plan's `depends_on` field must agree with it. A cycle is an error and a diamond is not. A plan routed `not_applicable` is bypassed to its nearest active ancestors (ADR-013 §4.5, ADR-034 ERR-034-06).
- **BRU-013-05 (Staleness Follows the Graph and Stops at the Branch):** An approval is fresh only if its own content hash matches, the hashes it recorded for its effective upstream plans match, and every transitive ancestor is itself fresh. A change marks only the downstream branch stale, even if the middle plan has not been regenerated. The answer names the plan that caused it (ADR-013 §4.5, Invariant 7; ADR-034 Transitive Staleness Law).
- **BRU-013-06 (Lifecycle State Is Derived, Never Stored):** A plan's governance state is computed at evaluation time from the file, the in-flight review, the latest adjudication and freshness, by a fixed precedence. A local edit outranks a past adjudication: an approved plan becomes `REAPPROVAL_REQUIRED`; a rejected or revision-requested plan returns to `DRAFTED` (ADR-013 §4.6, Invariant 9).
- **BRU-013-07 (Formalization Is Route-Conditioned and Names Its Blockers):** The PMP may be formalized only when every `full_plan` is approved and fresh, every `pmp_section` is present and not a stub, and every `not_applicable` plan has a recorded rationale. When it may not, the answer lists each blocking plan and why, so the failure points at a plan, not at the whole (ADR-013 §4.3, Invariant 1).
- **BRU-013-08 (Purity and Storage Boundary):** All of the above is plain data in, plain data out. It never imports the store, reads a file or calls the network; the runtime that does so is ADR-034's. No new `LearningStore` record type is added (ADR-002 Invariant #2). Gate decisions are `full`-authority scored audit evidence and never enter the learner (ADR-013 §4.9, ADR-001 §4.2).
- **BRU-013-09 (Plan-Level and Integration-Level Defects Are Attributed Differently):** A defect localized to one plan is attributed to that plan's gate; a defect that appears only when plans are combined is attributed to `approve-pmp` (ADR-013 §4.9). *This rule has no code deliverable in this epic; it is a convention for the reviewers and for the future `approve-pmp` build.*

## Stakeholder Success Metrics

| Metric | Target |
|---|---|
| Hash stability | The same plan text with LF, CRLF, a BOM, trailing whitespace or changed volatile fields gives one hash; any change to the body or to a static field gives a different one |
| Block coverage | Each of the four technical-integrity conditions has a test that rules `approve_plan` out; 0 floor, cap or provisional-token findings rule it out |
| Contract fidelity | An approval record built by the producer is read back by the reader without loss; 0 contract keys outside the ADR-034 schema |
| Graph correctness | The graph has no cycle; the nine plan ADRs' `depends_on` fields all agree with it; a diamond evaluates without a false cycle |
| Staleness | The ADR-034 normative scenarios (mixed-route staleness, omission bypass, raw hash) give the stated outcome; a change to a support plan stales no core plan |
| State determinism | Every combination of file, review, adjudication and freshness maps to exactly one lifecycle state |
| Formalization | 0 formalizations allowed with a missing, stale, stub or unrationalized plan; every refusal names its plans |
| Purity | 0 imports of storage, the legacy `pmbok/` or a third-party package; 0 new record types |

## Out of Scope

- The `agent-learn pmbok draft|approve|formalize|adapt` commands, the batch interactive dashboard, the runtime harness and every `LearningStore` read or write (ADR-034, its own epic).
- Building `approve-pmp` and its attribution of integration defects (ADR-008, ADR-013 Negative Consequences).
- The human review itself: scoring the four criteria for a real plan is evidence supplied at decision time.
- Adaptation mode (`--mode adapt`) and the `Adaptation-Plan.md` checklist (ADR-034 `pmbok adapt`).
- Porting the 49-process registry, the test-suite port and removing the legacy `pmbok/` directory (ADR-034).
- Cycle identity and cross-cycle traceability (ADR-035, Proposed).
