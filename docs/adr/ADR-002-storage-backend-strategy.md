# ADR 002: Storage Backend Strategy — Local File, In-Memory, and Cosmos DB

## 1. Executive Brief
The SDK persists exactly five durable record types (episode, metric result, reward, policy snapshot, training run) behind one abstract `LearningStore` interface, with three real, interchangeable implementations: `InMemoryStore` (tests/notebooks), `LocalFileStore` (single-process durable JSON files), and `CosmosStore` (shared, multi-process/multi-replica history). The rest of the SDK never imports a concrete backend — confirmed directly in `storage/base.py`'s own docstring. This decision — a narrow, record-type-scoped interface with exactly these three backends, selected by environment configuration rather than code branching — is real and already implemented, but has no decision record naming why three backends, why this interface shape, or what was rejected.

## 3. Context
- `storage/base.py`'s `LearningStore` is an `ABC` with abstract methods grouped by record type (Discovery, Episodes, Metric results, Rewards, Policy snapshots, Training runs) — confirmed directly, 19 abstract methods total, no concrete logic. Its own docstring states the design intent plainly: "New backends (Cosmos, SQL, in-memory) implement this protocol; the rest of the SDK never imports a concrete backend."
- **`TaskPolicy` is not itself one of the five durable record types.** `TaskPolicy` (`decision.py:848`) is a runtime-only wrapper constructed from a `PolicySnapshot` — it holds no independent persisted state. `decision_authority`, the complexity profile, and every other piece of policy configuration live inside `PolicySnapshot.metadata` (`types.py:379-418`), which is the actual record `store_policy()` persists. A reader of ADR-001 alongside this ADR could otherwise wonder whether `TaskPolicy` is a sixth record type; it is not.
- The single entry point that actually reads `AGENT_LEARNING_STORE_BACKEND` and resolves a concrete backend is `get_default_store()` (`storage/cosmos.py:477`, re-exported via `storage/__init__.py`) — this is how `cli.py` and the rest of the SDK obtain a store instance without ever importing `LocalFileStore`/`InMemoryStore`/`CosmosStore` by name.
- `LocalFileStore` (`storage/local.py`): file-per-record, atomic writes (temp file + `os.replace`), default root `./data/agent-learning/store`, overridable via `AGENT_LEARNING_LOCAL_STORE_DIR`. Its own docstring discloses a real, load-bearing limitation: "this backend is single-process (last writer wins); it does not coordinate concurrent writers across processes."
- `InMemoryStore` (`storage/memory.py`): explicitly scoped to "unit tests and single-process notebooks... data does not survive process exit" — not a production backend candidate at all, by its own docstring.
- `CosmosStore` (`storage/cosmos.py`): one container per record type (5 containers: episodes/rewards/metrics/policies/runs), partitioned by `agent_id`, lazily initialized (containers created on first use), confirmed via direct read. `azure-cosmos` is an optional dependency (`[cosmos]` extra in `pyproject.toml`) — importing `CosmosStore` without it installed does not crash at import time (guarded `try/except ImportError`), only at actual use (`_ensure_ready()` raises `RuntimeError` with an explicit remediation message naming `InMemoryStore` as the local-testing alternative).
- **`store_policy()`'s own two-write pattern, checked directly (`cosmos.py:381-393`), is more nuanced than "multi-process/multi-replica" safe without qualification.** It writes two documents: (1) the versioned snapshot itself (`policy.to_dict()`), safe under concurrent writers because `advance_version()` (`types.py:399-403`) mints a **fresh `id` on every version**, so no two versions ever contend for the same document; and (2) a separate `"active:<task_id>"` pointer document recording which `policy_id` is currently active, written via plain `_upsert()` → `upsert_item(doc)` (`cosmos.py:130-136`) with **no ETag or optimistic-concurrency check at all**. If two replicas both call `store_policy()` after computing updates from overlapping episode batches, whichever pointer write lands last wins — the exact same last-writer-wins hazard `LocalFileStore` discloses, narrowed to this one pointer document rather than the whole store, and not disclosed anywhere in this ADR's original draft.
- `CosmosConfig` supports three credential paths, in a real, explicit precedence order (`config.py`, confirmed directly): (1) an explicitly supplied `TokenCredential`, (2) a `credential_mode` string resolved into a credential via a lazy `azure-identity` import, (3) a legacy `api_key` path used only when neither of the first two is set. The default `database_name` is `"dq_rl"`.
- `docs/decision-making.md`'s own "Storage and deployment patterns" table already maps backend choice to four real deployment contexts (local development, Azure AI Foundry workload, AKS, Fabric notebook/Spark) — this is real, existing design rationale, just never captured as a decision record with named rejected alternatives.
- `docs/architecture.md` documents a specific, real Cosmos deployment topology for the Azure case: private endpoint only, no public access, VM managed identity, zero keys/secrets on the host — this is a concrete instance of credential path (1)/(2) above, not path (3).

## 4. Decision

### 4.1 One narrow interface, scoped to exactly five durable record types
`LearningStore` is deliberately narrow — five record types, no generic key-value escape hatch, no backend-specific methods leaking through the abstract interface. This is a real constraint, not an oversight: it's what makes three structurally very different backends (an ABC with zero shared implementation, local JSON files, Cosmos containers) swappable by configuration alone, with the rest of the SDK (confirmed: `decision.py`, `cli.py`, the learners/scorers) never importing a concrete backend.

### 4.2 Three backends for three genuinely different deployment shapes, not one backend with modes
`InMemoryStore` (ephemeral, single-process, tests), `LocalFileStore` (durable, single-process, explicitly not safe for concurrent writers), and `CosmosStore` (durable, multi-process/multi-replica, partitioned by `agent_id`) are not three configurations of one storage engine — they solve three different real problems (no persistence needed; persistence needed but one process; persistence needed across many processes/replicas). `LocalFileStore`'s own disclosed "last writer wins" limitation is the concrete reason a fourth option — "make `LocalFileStore` safe for concurrent writers" — was not pursued; Cosmos already solves that problem for the cases that need it. **Qualified in §4.5**: this holds fully for episode/reward/metric/training-run inserts and for the versioned policy-snapshot history itself, but not yet for the active-policy pointer document specifically.

Furthermore, `CosmosStore` natively supports running in local environments (e.g., local Docker or local Kubernetes/AKS Edge/k3s clusters) against the official Azure Cosmos DB Emulator using the local shared-key authentication path (`AGENT_LEARNING_COSMOS_AUTH_MODE="key"`). This allows multi-replica and concurrency testing with 100% behavioral parity with cloud Azure Cosmos DB without requiring developers to maintain, provision, or pay for an active Azure cloud subscription during the development and CI phases.

### 4.3 Cosmos credential resolution defaults to identity-based, not key-based
The three-path precedence (§3) treats an API key as the legacy fallback, not the primary path — consistent with `docs/architecture.md`'s real deployment topology (managed identity, zero keys on the host). This is a real security-posture decision: a new integration that only sets `credential_mode` never touches a secret at all.

### 4.4 Cosmos backend is optional at the dependency level, not just at the configuration level
`azure-cosmos` being an optional extra (not a base dependency) means a user who never configures Cosmos pays no import cost and faces no hard dependency — the guarded `try/except ImportError` at module load time, deferring the real failure to first actual use with a specific remediation message, is deliberate UX, not defensive boilerplate.

### 4.5 Known gap: the active-policy pointer is not safe under concurrent multi-replica writes
Checked directly against `CosmosStore.store_policy()` (§3), the "multi-process/multi-replica" safety claimed for Cosmos in §4.2 does not fully hold. New episodes, rewards, metrics, and training runs are each independently-keyed documents — concurrent inserts across replicas genuinely don't conflict. Policy snapshots are also safe across versions, because `advance_version()` mints a new `id` every time. But the `"active:<task_id>"` pointer — the document that says which `policy_id` is currently active for a task — is overwritten via plain `upsert_item()` with no ETag or optimistic-concurrency guard. Two replicas racing to finish a training update for the same `(agent_id, task_id)` can leave that pointer referencing whichever write landed last, **including regressing to an older version even though a newer one has already been successfully persisted elsewhere** — the risk here is not data loss (both snapshots survive independently), it is activation of stale policy state. This is a real, disclosed gap, not a hypothetical: the same failure mode `LocalFileStore`'s own docstring already admits, just narrower in scope here. **Preferred remediation, named but not built here:** an ETag-conditioned replace on the pointer write, retrying on conflict — not a distributed lock or lease, unless that simple approach proves insufficient. Closing it is real, scoped future work, not resolved in this ADR, which only records that the gap exists, exactly where, and the direction a fix should take.

### 4.6 Non-goal: `LearningStore` is not a query or analytics platform
Stated explicitly rather than left implicit: this abstraction exists to persist and retrieve the five named record types for the SDK's own learning loop. It does not provide ad hoc analytics, reporting, vector search, feature storage, or general-purpose document management. Any future need along those lines is a different system's job, layered on top of (not merged into) `LearningStore` — naming this boundary now is cheaper than discovering it by scope creep later.

## 5. Alternatives Considered

| Alternative | Reason for rejection |
|---|---|
| A single configurable backend (e.g., always Cosmos, with a "local emulator" mode for development) | Would force the Cosmos SDK as a base dependency and the Cosmos emulator as a development requirement for every user, including those who only ever run single-process local workflows — contradicts the explicit "no GPU, no heavy infra required" positioning in `docs/decision-making.md`. |
| Make `LocalFileStore` safe for concurrent multi-process writers (e.g., file locking) | Would add real complexity to the backend specifically scoped for single-process durable use, duplicating what Cosmos already does correctly for the multi-process case — the docstring's explicit disclosure of the limitation, rather than a silent fix, suggests this was a deliberate scope boundary. |
| A generic key-value `LearningStore` interface instead of five record-type-scoped method groups | Would let callers store arbitrary shapes, breaking the guarantee that the rest of the SDK can reason about exactly five durable record types — the "one container per record type" Cosmos schema and the atomic one-file-per-record `LocalFileStore` layout both depend on the interface already knowing what it's persisting. |
| Default Cosmos credential resolution to `api_key` for simplicity | Contradicts the real, already-built private-topology deployment pattern (managed identity, zero secrets on the host) documented in `docs/architecture.md` — defaulting to keys would make the common Azure deployment path the one requiring extra configuration, not the other way around. |
| A fourth, relational/SQL backend (the possibility `storage/base.py`'s own docstring names: "Cosmos, SQL, in-memory") | Never built, and not an oversight: all five record types are self-contained documents keyed and queried by `agent_id`/`task_id`, with no cross-entity relational joins the SDK actually needs. `LocalFileStore` already covers zero-setup local durability, and `CosmosStore` (via the local Cosmos DB Emulator) already covers local multi-replica testing without cloud subscription costs, while scaling seamlessly to managed Azure Cosmos DB in production. A relational/SQL backend would add schema, migration (Alembic), and ORM (SQLAlchemy) maintenance for a document query shape nothing currently requires. Deferred, not rejected: the docstring's own phrasing was aspirational at the time it was written, not a commitment this ADR is now breaking. |

## 6. Consequences

### Positive
- Swapping backends is a configuration change (`AGENT_LEARNING_STORE_BACKEND`), never a code change, because the interface boundary is real and complete — confirmed by grep: no file outside `storage/` imports a concrete backend class directly in the SDK's own runtime code.
- The Cosmos extra being genuinely optional means the SDK's base install stays lightweight for the common local-development and notebook cases.
- Identity-first credential resolution matches the zero-secrets deployment topology already built, rather than requiring a second hardening pass later.
- Zero-subscription development phase: `CosmosStore` runs entirely offline and locally via the official Cosmos DB Emulator (in Docker or local AKS clusters), providing full multi-process/multi-replica concurrency parity without requiring active cloud infrastructure or subscription maintenance costs during development and CI.

### Negative
- `LocalFileStore`'s disclosed concurrency limitation means any user who outgrows single-process use must migrate to Cosmos — there is no intermediate "local but multi-process-safe" option. **Migration itself is explicitly out of scope**: the SDK guarantees record compatibility through the `LearningStore` contract (the same `to_dict()`/`from_dict()` shapes work against any backend), but provides no automated export/import tooling between backends today — naming that boundary here rather than leaving it to be assumed.
- Three real backends means three real code paths to keep behaviorally identical against the same abstract contract — a bug in one backend's handling of a method (e.g., an edge case in `query_episodes`'s date filtering) could silently diverge from the other two without a shared contract-test suite enforcing parity (not confirmed either way in this pass whether such a suite exists; a future ADR on contract testing, not this one, would be the place to decide that).
- `CosmosStore`'s active-policy pointer is not safe under concurrent multi-replica writes to the same `(agent_id, task_id)` (§4.5) — a real, narrower version of the same hazard `LocalFileStore` discloses for itself, not yet closed.

## 7. Architectural Invariants

1. All durable SDK state flows through `LearningStore` — no backend-specific method leaks through the abstract interface.
2. Only the five named record types (episode, metric result, reward, policy snapshot, training run) are persisted through it; `TaskPolicy` itself is not a sixth type (§3).
3. Code outside `storage/` never imports a concrete backend class — only the abstract `LearningStore` protocol (for type annotations, confirmed real: `training/runner.py`, `capture.py`, `audit.py`, `autonomy.py`, `rewards/writer.py` all import it this way) and `get_default_store()` (§3).
4. Backend selection is configuration-driven (`AGENT_LEARNING_STORE_BACKEND`), never a code branch.
5. A policy snapshot's `id` changes on every version (`advance_version()`); only the active-policy pointer document is mutated in place, and only that pointer currently lacks concurrency protection (§4.5).
6. `LearningStore` persists and retrieves the five named record types only — it is not a query or analytics platform (§4.6).
